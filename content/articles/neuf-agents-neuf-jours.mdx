J'ai fait tourner une flotte d'agents SRE autonomes sur mon infrastructure réelle : un home-server, un DGX Spark et un VPS. La boucle agentique a fonctionné. La valeur produite pour l'infra, beaucoup moins. Voici les chiffres, ce qui a tenu, ce qui a cassé, ce que l'analyse des traces m'a appris, et ce que je garde.

## Le dispositif

Le projet est né pour le NVIDIA Claw Agent Challenge à Paris : montrer un agent SRE capable de surveiller, diagnostiquer et réparer une infrastructure sans humain dans la boucle. J'ai utilisé [Hermes Agent](https://github.com/NousResearch/hermes-agent), un LLM servi en local par vLLM sur un DGX Spark (Qwen3.8), et un serveur MCP maison de 59 outils couvrant mes trois machines : lecture, écriture Docker sous garde-fous, exécution en bac à sable.

Après le challenge, la flotte a continué à tourner sur mon home-server avec des rôles séparés. Un seul agent, le conductor, a le droit de créer des tâches. Les autres rendent des verdicts.

```text
cron */10 ─┐
           ├─▶ sre-conductor ──Kanban──▶ sre-monitor   (scan read-only, classe, rapporte)
webhook ───┘   (seul dispatcher)          ├─▶ sre-diag      (cause racine → verdict, n'applique rien)
(crash, OOM)                              ├─▶ sre-doctor    (hot-fix infra à partir d'un verdict)
                                          ├─▶ sre-dev       (correctif de code en TDD → PR)
                                          └─▶ sre-reporter  (seul à notifier l'humain, Telegram)

à côté : sre-hygiene (nettoyage des incidents), auto-eval (juge les traces), gardien (rappels)
observabilité : Langfuse (traces par profil) + Julia-1, petit modèle de décision qui note chaque étape
```

## Lire les traces pour faire évoluer les agents

C'est la partie de l'expérience qui m'a le plus appris. Chaque appel d'outil de chaque agent finit dans Langfuse. Plutôt que de lire des transcripts à la main, j'ai construit un pipeline qui détecte les appels en échec, les classe, et réécrit le verdict sur la trace sous forme de score.

Le classement repose sur une question simple : à qui est la faute ? Quatre catégories en sont sorties.

Deux choses m'ont surpris. D'abord, sept règles déterministes suffisent à classer 88 % des échecs. Le LLM n'intervient que sur le résidu, et ses classements récurrents ont vocation à devenir de nouvelles règles. C'est le seul endroit de la flotte où le système devenait moins dépendant du modèle à mesure qu'il tournait.

Ensuite, la catégorie la plus grosse n'était pas une erreur de l'agent. Près de la moitié des échecs relevaient de « capacity » : l'agent voulait faire quelque chose de raisonnable et l'environnement le lui interdisait. En mode autonome, sans humain pour approuver, l'exécution de code et le terminal sont refusés par le harnais : 111 refus sur l'exécution de code, 69 sur le terminal. Ces chiffres sont devenus une liste de besoins. J'ai créé des outils MCP étroits pour les couvrir : une exécution de commandes en lecture sur liste blanche, un Python en bac à sable sans réseau ni secrets, une sonde HTTP limitée à des cibles internes.

Les échecs « reasoning » racontaient autre chose. Une bonne partie venait de l'outil intermédiaire qui sert à appeler les outils chargés à la demande : le modèle se trompait d'arité ou appelait directement un outil qui devait passer par lui. Ces motifs se corrigeaient dans les fichiers d'instructions des agents, pas dans le code : un skill dédié à l'usage des outils, des exemples d'appels corrects, et des consignes retirées quand elles se contredisaient.

Le même travail a guidé la gestion de la fenêtre de contexte. Charger d'emblée les schémas de 59 outils noie le modèle. Les outils sont donc découverts à la demande, avec une liste plafonnée à 12 000 tokens, chaque profil n'a accès qu'aux outils de son rôle (27 pour le diagnostic, par exemple), et ne charge automatiquement que ses propres skills. J'ai aussi réglé l'effort de raisonnement par rôle : faible pour l'orchestration, élevé pour la sonde qui doit juger un état ambigu.

La difficulté de fond, c'est de faire évoluer un agent dans un environnement protégé. Chaque restriction de sécurité crée une nouvelle catégorie d'échecs « capacity ». L'agent a besoin d'outils, mais les outils prévus ne couvrent jamais tous ses besoins réels. Il faut donc mesurer ce qu'il essaie de faire, distinguer le besoin légitime du contournement, puis ajouter l'outil le plus étroit possible. L'audit du 6 octobre l'a montré dans l'autre sens : quand l'outil manquait, l'agent passait par le terminal et le socket Docker. Une partie des échecs « capacity » qui disparaissaient n'étaient pas résolus. Ils étaient contournés.

## Ce que je ferais autrement

<Lesson title="Déclencher sur un événement">
Un agent ne doit travailler que quand quelque chose de nouveau arrive : une alerte, une PR, un document. La détection elle-même n'a pas besoin de LLM. Aujourd'hui, Uptime Kuma et un script de 120 lignes envoient directement les alertes sur Telegram.
</Lesson>

<Lesson title="Le LLM explore, le code consolide">
Chaque passage d'un agent devrait laisser un artefact qui réduit le besoin du passage suivant : une règle, un test, une ligne de dataset. La classification des échecs d'outils le faisait déjà en transformant les classements du LLM en règles. C'est ce mécanisme qu'il fallait généraliser, pas le scan.
</Lesson>

<Lesson title="Mesurer ce que l'agent essaie de faire">
Les échecs d'outils sont la meilleure spécification des besoins d'un agent. Les classer par responsabilité (environnement, raisonnement, charge) dit quoi corriger et où : un outil à ajouter, une consigne à réécrire, ou rien.
</Lesson>

<Lesson title="Le moindre privilège dès le premier jour">
Un agent qui a un terminal a tout ce qui est monté dans son conteneur. La bonne frontière n'est pas une liste d'outils autorisés, c'est ce que le conteneur peut atteindre : un proxy Docker en lecture et une clé SSH limitée à trois commandes validées côté hôte.
</Lesson>

<Lesson title="Vérifier par le chemin réel">
Le gateway transmet un environnement filtré aux serveurs MCP. Mes tests passaient par docker exec, qui voit tout : ils étaient verts, les agents étaient aveugles. Seule une vraie session d'agent prouve qu'un outil marche.
</Lesson>

<Lesson title="Mesurer par profil dès le départ">
L'attribution des traces par profil est arrivée tard : deux tiers des tokens ne sont rattachables à aucun agent. Sans cette mesure, on ne voit pas qu'une boucle coûte 60 fois plus que le travail utile.
</Lesson>

## Ce que je garde

| Brique | Ce qu'elle apporte |
| --- | --- |
| Agent sans root | Proxy Docker en lecture et redémarrage, passerelle SSH à commandes épinglées, une seule clé montée. |
| Classification des échecs d'outils | Règles d'abord, LLM sur le résidu, verdict réécrit sur chaque trace Langfuse. |
| Juge Julia-1 sur Langfuse | Évaluation typée de chaque étape et de chaque tour, sur CPU, branchée comme évaluateur natif. |
| Collector OpenTelemetry | Un seul point d'entrée : traces d'infra vers Jaeger, spans LLM vers MLflow. |
| Secrets Bitwarden | Injection au lancement, pour Docker Compose comme pour les agents, rien sur disque. |

La flotte reste reproductible à partir d'un tag git. Ses crons sont en pause, pas supprimés. La prochaine expérience part d'une hypothèse plus étroite : donner à chaque service consommateur de LLM son propre compte et ses propres clés via le gateway MLflow.
