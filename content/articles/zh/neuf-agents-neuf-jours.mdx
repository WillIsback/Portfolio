## 装置

这个项目是为巴黎的 NVIDIA Claw Agent Challenge 而生的：展示一个能在回路中没有人类的情况下监控、诊断并修复基础设施的 SRE 智能体。我用了 [Hermes Agent](https://github.com/NousResearch/hermes-agent)、一个由 vLLM 在 DGX Spark 上本地推理的 LLM（Qwen3.8），以及一个自研的、覆盖三台机器的 59 工具 MCP 服务器：读取、受护栏约束的 Docker 写入、沙箱执行。

挑战赛之后，集群继续在我的家用服务器上运行，角色彼此独立。只有一个智能体——conductor——有权创建任务。其余智能体只给出裁决。

```text
cron */10 ─┐
           ├─▶ sre-conductor ──Kanban──▶ sre-monitor   (只读扫描，分类，上报)
webhook ───┘   (唯一调度者)                    ├─▶ sre-diag      (根因 → 裁决，不执行任何操作)
(crash, OOM)                              ├─▶ sre-doctor    (依据裁决热修基础设施)
                                          ├─▶ sre-dev       (以 TDD 修代码 → PR)
                                          └─▶ sre-reporter  (唯一向人类告警者，Telegram)

另外：sre-hygiene（清理事件）、auto-eval（评判轨迹）、gardien（提醒）
可观测性：Langfuse（按配置的轨迹）+ Julia-1，一个小型决策模型，为每一步打分
```

## 读轨迹，让智能体进化

这是整个实验里让我学到最多的部分。每个智能体的每次工具调用都进入 Langfuse。与其手动读 transcript，我搭了一条流水线：检测失败的调用、给它们分类，并把裁决以分数的形式写回轨迹。

分类基于一个简单的问题：这是谁的错？由此得出四个类别。

有两件事让我意外。第一，七条确定性规则就足以给 88% 的失败分类。LLM 只处理剩下的残差，而它反复出现的分类，本就是要变成新的规则。这是整个集群里唯一一处：系统越跑，对模型的依赖反而越少。

第二，最大的类别并不是智能体的错误。近一半的失败属于「capacity」：智能体想做一件合理的事，环境却不允许。在自主模式下，没有人来批准，代码执行和终端会被 harness 拒绝：代码执行被拒 111 次，终端被拒 69 次。这些数字变成了一份需求清单。我为此造了窄范围的 MCP 工具：白名单上的只读命令执行、无网络无密钥的沙箱 Python、只针对内部目标的 HTTP 探测。

「reasoning」失败讲述的是另一回事。相当一部分来自那个用来调用按需加载工具的中间层工具：模型搞错了参数个数，或者直接调用了本该经由它转发的工具。这些模式是在智能体的指令文件里修正的，而不是在代码里：一个专门讲工具用法的 skill、一些正确调用的示例，以及删掉那些自相矛盾的指令。

同样的工作也指导了上下文窗口的管理。一上来就加载 59 个工具的 schema 会把模型淹掉。所以工具是按需发现的，列表上限为 12,000 token；每个配置只能访问属于自己角色的工具（比如诊断有 27 个），并且只自动加载自己的 skill。我还按角色调整了推理强度：编排用低强度，需要判断模糊状态的探测用高强度。

根本的难处在于：让一个智能体在受保护的环境中进化。每一条安全限制都会催生出一类新的「capacity」失败。智能体需要工具，但预设的工具永远覆盖不了它全部的真实需求。所以必须测量它想做什么，区分正当需求与绕过行为，然后补上尽可能窄的工具。10 月 6 日的审计反过来证明了这一点：当工具缺失时，智能体就走了终端和 Docker socket。那些消失的「capacity」失败里，有一部分并没有被解决，而是被绕过了。

## 如果重来，我会怎么做

<Lesson title="由事件触发">
智能体只应该在有新东西出现时才工作：一条告警、一个 PR、一份文档。检测本身并不需要 LLM。如今，Uptime Kuma 和一个 120 行的脚本直接把告警发到 Telegram。
</Lesson>

<Lesson title="LLM 负责探索，代码负责沉淀">
智能体每跑一次，都应该留下一个能减少下一次需求的产物：一条规则、一个测试、一行 dataset。工具失败的分类已经在这么做了，它把 LLM 的分类变成规则。该推广的是这个机制，而不是扫描。
</Lesson>

<Lesson title="测量智能体想做什么">
工具失败是一个智能体需求最好的规格说明。按责任归类（环境、推理、载荷）能告诉你该修什么、修哪里：加一个工具、重写一条指令，还是什么都不用做。
</Lesson>

<Lesson title="从第一天起就最小权限">
一个有终端的智能体，就拥有了挂载进它容器里的一切。正确的边界不是一份允许的工具清单，而是容器能触及什么：一个只读 Docker 代理，和一把在宿主机侧被限制为三条校验命令的 SSH 密钥。
</Lesson>

<Lesson title="走真实路径来验证">
gateway 把过滤后的环境传给 MCP 服务器。我的测试走的是 docker exec，它能看到一切：测试是绿的，智能体却是瞎的。只有一次真实的智能体会话才能证明某个工具能用。
</Lesson>

<Lesson title="从第一天就按配置测量">
按配置的轨迹归属来得很晚：三分之二的 token 无法归到任何智能体。没有这项测量，就看不到一个回路比有用工作贵 60 倍。
</Lesson>

## 我保留什么

| 组件 | 它带来什么 |
| --- | --- |
| 无 root 的智能体 | 只读 Docker 代理与重启、固定命令的 SSH 网关、只挂载一把密钥。 |
| 工具失败的分类 | 规则优先，残差交给 LLM，裁决写回每条 Langfuse 轨迹。 |
| Langfuse 上的 Julia-1 裁判 | 对每一步、每一轮做带类型的评估，跑在 CPU 上，作为原生 evaluator 接入。 |
| OpenTelemetry collector | 单一入口：基础设施轨迹发往 Jaeger，LLM span 发往 MLflow。 |
| Bitwarden 密钥 | 启动时注入，Docker Compose 和智能体都如此，磁盘上不留任何东西。 |

整个集群可以从一个 git tag 复现。它的 cron 只是暂停，并未删除。下一次实验从一个更窄的假设出发：通过 MLflow gateway，让每个消费 LLM 的服务都有自己的账户和密钥。
