自动校对工具有个副作用：把文本粘贴进去，复制结果，什么也没学到。Grammaria 保留了校对工具的速度，并加了一层观察：它指出每一处错误的名称，找出反复出现的错误，并在用户复制的那一刻简短地告诉他。0.5 测试版于 2026 年 11 月 21 日发布。为了走到这一步，我必须把过于笨重的语法引擎换成自己用 Rust 写的引擎：grammaria-rc。下面把两者都讲一遍。

## 从 ai_corrector 到 Grammaria

项目始于 2026 年 3 月 30 日，当时叫 ai_corrector：一个编辑器、一次对语言模型的调用、一个差异显示。它的 README 将其介绍为“由 LLM 驱动的法语写作校对与改写工具”。

6 月底，我在已知正确答案的错误句子上比较了两种可能的做法。语言模型复现参考答案的程度远好于 LanguageTool（基于规则的开源校对工具）：平均得分 0.93 对 0.76（BLEU 与 ROUGE-L 的平均值，模型用了 50 个句子，LanguageTool 用了 200 个，所以只能当作参考）。模型纠错更好。但它无法稳定地说出自己纠正的是_哪一种_错误。LanguageTool 却可以：每一次检测都带有一条规则的名称。

于是有了 Grammaria 的核心思路：不二选一。模型负责纠错，规则引擎负责解释。

## 纠错和解释，是两件分开的事

1. **语言模型只负责纠错，别的什么都不做。** 它只返回纠正后的文本，边生成边显示。**复制**按钮从最初几个词开始就能用。让它同时给出修改清单，会拉长回答，而且这份清单每次都不一样。
2. **Grammaria 通过逐词比较原文和纠正后的文本，计算出修改。** 这个计算是确定性的，不占用模型的任何开销。
3. **语法引擎在原文中为错误命名**，与上面并行。只有模型确实改动了那一段时，才采纳这条检测，这样就排除了误报，比如被错误标出的专有名词。

模型由用户自己选择：自己电脑上的 Ollama、内部服务器上的 vLLM，或任何兼容 OpenAI 的 API。文本只会发往这一个地方。错误分析、日志和进步统计都留在本机。

## 反复出现的错误

错误有了名称，Grammaria 就能统计它们。一份本地日志为每个错误保存规则标识符（例如 `PAIRE:a/à`，法语中读音相同的 a 与 à 的混淆）、类别和日期。当某个错误再次出现，复制按钮旁会显示一条提示；再下一次，则是二选一的选择题。没有任何东西会拖慢复制：赶时间的人要的是干净的文本，不是一堂课。十三种常见混淆（_a/à_、_on/ont_、_ces/ses_、_-er/-é_……）各有一张“用 X 替换，因为 Y”的卡片。一个满分 20 的评分、一个**进步**页面和十八枚朴素的徽章展示已走过的路，没有不能中断的连续天数。

到 0.4 为止，日志还会保存句子。0.5 不再保存任何内容：没有句子，没有词，没有修改，也没有规则消息（它可能引用文本里的词）。现有的日志在更新时会被清理，连文件本身也一并处理。为了证明这一点，测试会纠正含有极罕见词的文本，比如“Kwaxolotl”或“zorglubienne”，然后在日志的字节里以及所有查询路由的响应里搜索它们。只要找到一个词，测试就失败。构建好的应用在 Linux 和 Windows 下都用同样的方式验证。

## 瓶颈：930 MiB 的 LanguageTool

到 0.3 为止，规则引擎是 LanguageTool 6.9 的 JavaScript 移植版 `@valueerror/ltjs`。它能完成工作，但代价很高：启动要 4.3 到 4.6 秒，内存超过 900 MiB。在桌面应用里，校对工具要在启动后约六秒才就绪，整个应用占用约 1.1 GB。对一个顺手就要打开的工具来说，这是不可接受的。

完整重写一个语法校对器是不现实的。不过，LanguageTool 对法语的全部智慧都在数据文件里：XML 格式的 5,343 条语法规则和 1,674 条风格规则、一部含 666,726 个词形的词典、消歧规则。执行这些的代码是一条界限清晰的分析链。移植这条链，并原样读取这些数据，是够得着的。

## grammaria-rc：先复现，再改进

我给自己定的规矩是：先**做到与原版一致**，逐项结果一致，然后才动手改。没有这一步，就无法知道某个差异来自改进，还是来自移植的 bug。

这项工作是和 Claude Code 智能体一起完成的：仓库 125 次提交中有 75 次由 Claude 共同署名。让它能在一天内完成的，是 **oracle**。一个脚本在任意文本上运行原版，输出它的结果，或分析每一步的标签。另一个脚本按原因对每个差异分类。这样，智能体在任何时刻都有一个可测量的目标：不必争论某条规则，只要看两个引擎是否在同一位置说了同样的话。

结果如下，只使用 LanguageTool 的规则，在 29,047 条文本上：

| | |
| --- | --- |
| 结果与原版完全一致的文本 | 29,038（99.97%） |
| 找回的原版检测（规则相同、位置相同） | 22,168 条中的 22,159 条 |
| 其中建议也相同的比例 | 99.65% |
| 分析（词、标签、消歧）完全一致 | 500,000 个词元（词和标点）中的 500,000 个 |

缺失的九条检测中，有七条是原版的误报：一条重复词规则在“on dit ou on écrit”（法语“人们说还是人们写”）上被触发。建议上的差异出在拼写上，而这里是 JavaScript 移植版偏离了 Java 版的 LanguageTool：对照 Java 验证后，grammaria-rc 的建议与 LanguageTool 相同。

<Lesson title="先做到一致，再超越">
一个可执行的 oracle 把含糊的移植变成一系列测量。编程智能体面对量化目标时工作得很好；面对“照 LanguageTool 的样子做”时则做得很差。
</Lesson>

## 然后做得比原版更好

一旦达到一致，引擎就可以分道扬镳了。它加入了 1,320 条自有规则，采用与 LanguageTool 相同的 XML 格式，并附有 3,081 个经过测试的例句：经由 _être_ 和系动词的过去分词与形容词一致、连词后的语式、应使用的不定式、686 条混淆规则（_a/à_、_peu/peut_、_différent/différend_……）、名词短语、排版。当其中一条规则与 LanguageTool 的某条规则标出同样的词时，保留 LanguageTool 的那一条。

此外还有一个**配置档**：LanguageTool 的七条规则被关闭，因为它们主要在写得好的文章上造成干扰；而像专有名词或缩写的未知词，不再被标为错误。在百科和文学类文章上，原版 3,800 条拼写警报中有 3,100 条其实是 _Fogg_ 或 _Allahabad_ 这样的名字。

这些数字要连同一项保留意见一起看，我把它写在了引擎的 README 里：自有规则是针对一个测试集写的，也就是 Grammalecte 的测试句子。在编写期间从未查看过的那一半上，它们使检出率提高了 6.5 个百分点，而在用来调整规则的那一半上是 13.5 个百分点。提升是真实的，但只有训练集让人以为的一半。

对一个每天使用的工具来说，另一项要紧的测量是误报。在 23.4 万词的精心润色、被认为正确的文章上，原版每 1,000 词触发 21.6 次警报，grammaria-rc 为 8.8 次。而在所有测试集上，被正确地放过的正确文本从 63.8% 升到 67.0%。

## 更快，更轻

| | 原版 | grammaria-rc |
| --- | --- | --- |
| 启动（全部加载，首次检查） | 4.3–4.6 秒 | **0.5 秒** |
| 内存 | 924–937 MiB | **220–250 MiB** |
| 160 词的文本，首次检查 | 531–608 毫秒 | **124–180 毫秒** |
| 同一文本，引擎已预热 | 179–192 毫秒 | **47–58 毫秒** |

在 Grammaria 里，这体现为：桌面应用的校对工具在启动后约 1.5 秒就绪，而不是六秒，内存从约 1.1 GB 降到 0.63 GB。Docker 服务器从 1,087 MB 降到 290 MB。引擎还经受了 40,000 条随机变异文本（表情符号、排版撇号、不换行空格、其他文字系统、超长行）的考验，没有崩溃。

grammaria-rc 独立于 Grammaria：它是一个 Rust 库（`Engine` 可在线程间共享）、一个能输出 LanguageTool JSON 格式的命令行工具，以及一个只加载一次数据的服务器模式。规则文件原样读取：改一个文件就能改变校对器，无需构建步骤。

## 测试版：验证它确实让人进步

纠错本身已经过检验：我几个月来每天都在用。而提示的效果从未被验证过。这正是 0.5 测试版的全部意义，我宁愿直说，也不愿让人去猜。

问题很简单：一条提示之后，某个错误出现的频率是否比之前低？几位志愿者像往常一样使用 Grammaria，持续四到六周，然后如果他们愿意，就提交一个数字文件。这个文件不含任何文本，也不含任何日期，保存之前会完整展示给用户，而且 Grammaria 自己从不发送它。对每个收到过提示的错误，**进步**页面会比较它之前和之后的频率，并与打字错误的频率对比，后者作为对照。

参与者很少，也没有随机分组，所以结果只是一个迹象，不是证明。测试版页面明确这样写了。

## 还缺什么

- **对进步的效果仍有待证明。** 如果提示毫无改变，Grammaria 仍会是一个好用的校对工具，而“帮你不再重复同样的错误”这个承诺就必须撤下。
- **没有 Mac。** 只支持 Windows 和 Linux。
- **Docker 服务器只支持一个用户，没有身份验证。** 自 0.5.1 起，它只监听托管它的那台机器；要向其他电脑开放，需要一个带身份验证的反向代理。
- **文本会发往所选的模型。** 使用本机或内部服务器上的模型时，没有任何内容离开单位；使用在线服务商时，文本会发给对方。桌面应用没有锁定的设置来阻止这一点。
- **引擎只支持法语**，也不包含 LanguageTool 的统计规则和远程规则。

## 让这一切成为可能的

Grammaria 采用 GPL-3.0 许可证，它的引擎采用 LGPL-2.1，也就是 LanguageTool 的许可证。引擎完全建立在其他开源项目的工作之上：**LanguageTool**（Daniel Naber 及其贡献者），其法语规则文件和词典被原样读取，其分析链从 Java 移植到了 Rust；**Grammalecte 和 Dicollecte**（Olivier R.），词典源自它们，其测试句子则被用作编写自有规则的测试集，依据的是预期行为，没有引用任何代码；**Morfologik**（Dawid Weiss 和 Marcin Miłkowski），其词典读取器和拼写检查器被移植到了 Rust。

Grammaria 可在 [grammaria.fr](https://grammaria.fr) 下载，引擎在 [GitHub](https://github.com/WillIsback/grammaria-rc) 和 crates.io 上。[解决方案](/solutions/grammaria)页面概述了这个应用的功能。
