我是法国的公职人员。要在会议中使用 Granola 这类云端笔记工具，需要走一道层级审批，而审批耗时会比这个工具本身的寿命还长。所以我做了 Syntheo：一个开源的会议笔记本，用运行在我自己电脑上、或运行在单位内部服务器上的模型来转写会议并撰写纪要。0.7.0 测试版于 2026 年 11 月 10 日发布。下面讲它为什么存在、包含什么、我如何交付它，以及还缺什么。

## 为什么要完全本地

需求很简单：开会时记笔记，实时看到转写，会后得到一份干净的纪要。做得很好的工具早就有了。它们把会议的音频和文字发送到厂商那里，而这恰恰是公共机构不经过漫长审批就做不到的事。

Syntheo 反过来处理这个问题：什么都不离开用户的环境。没有账号，没有遥测，没有加入通话的机器人。应用采集麦克风和系统声音，把音频发送到用户自选的转写服务器，再向用户同样自己托管的语言模型请求纪要。音频只在内存中停留到转写完成，随即消失。

在 2026 年，这个硬件假设是合理的：一个约 8 亿参数的转写模型加一个中等规模的语言模型，可以跑在使用 MLX 的 Mac、一张 RTX 3090 或一台 DGX Spark 上。这相当于一台配置较好的办公电脑，或一个部门共用的服务器。它覆盖不了所有人，这也是这个项目最主要的局限。

## 从分叉到身份

我不是从零开始的。Syntheo 分叉自 Anarlog，一个 MIT 许可的会议笔记应用。我先给它改了名，然后重做：法语界面、由用户配置的服务器，以及一套我称为“绿茶”的视觉识别。

名字读作 Syn·thé·o，thé 在法语里是“茶”：围绕茶聚在一起的东西。在日本，茶会（chakai）把主人和客人聚在一起。之后，一位与会者会留下“会記”（kaiki），也就是他自己对这次聚会的记录；已知最早的会記，例如《松屋会記》，始于 1533 年。这个意象对我来说更像需求说明，而不是装饰：

- **纪要从用户的笔记出发**：Syntheo 用转写来补充笔记，而不是替换它们。用户的笔记保持绿色，补充的文字用墨色；
- **从不保留音频**，这是原则：一期一会，“一生只有一次的相遇”；
- **完成的笔记会盖上“記”字印章**，意为“记录”，正是“会記”里的那个字。

Syntheo 之前还有一代：一个 Next.js 加 PostgreSQL 的网页应用，现已改名为 `Syntheo-web`。桌面应用接过了这个名字。

## 0.7.0 包含什么

0.7.0 运行在 Linux 和 Windows 上，基于 Tauri 2（Rust）和 React 19 构建，使用本地 SQLite 数据库。实时转写通过 NVIDIA NIM 或经由 speaches 的 Whisper 完成，撰写则可以使用任何兼容 OpenAI 的 API（vLLM、Ollama、MLX）。DTLN 回声消除（ONNX）防止扬声器的声音再从麦克风回来。

这一批次新增的内容：

- **项目文件夹**：每个文件夹一页，带有一条由模型按需更新的“主线”，它保留用户的修改，并链接回来源会议。基于这条主线，Syntheo 会提出**下一次会议**的议程并预先准备笔记。
- **自动化**：只有一个模型，七种动作（包括“提取任务”），可从菜单或用 **Ctrl+J** 启动。敏感动作（webhook 和系统命令）需要确认。
- **收听**：麦克风和系统声音可以**分别**静音；一个悬浮小窗可以暂停和继续，不必回到主窗口。
- **导入**音频和视频文件，只需实时模型即可，显示进度，网络中断后可无重复地继续。

## 清理

这一批次有一部分是看不见的。在开启一个次版本之前，我会测量代码并删除不再使用的部分。这次删除了日历、云同步与共享、Pro 订阅和旧的保险库。它们都是分叉遗留下来的东西，在一个没有账号、没有厂商服务器的应用里毫无意义。

对我来说最重要的是最后一个数字。一个太长的文件，无论人还是智能体都不会完整读完。清理是有代价的：两次无法回退的数据库迁移。升级到 0.7.0 的数据库不能再用 0.6.x 打开，应用会明确告诉用户，而不是直接出错。

## 方法

这是我最满意的部分，因为它在保持节奏的同时没有放弃验证。

**按版本分批。** 每个版本就是一个批次：一个 `feat/0.7.0` 分支，每个 issue 一个子分支，再用唯一一个 PR 把整个批次合入 `main`。修复先于新功能，合并后自动发布。版本号根据提交信息计算。

**分布在三台机器上的 Claude Code 智能体。** 一个会话在我的家用服务器上负责编排：拆分工作、创建 issue、撰写 PR。一个通过 Remote Control 运行在 32 核台式机上的会话负责编译和跑重量级测试。第三个会话在 DGX Spark 上，负责部署和测试模型。

```text
家用服务器 ── 编排会话：issue、子分支、PR、待确认检查
   │
   ├─▶ 32 核台式机（Remote Control）：Rust 编译、测试、alpha
   └─▶ DGX Spark：转写模型和语言模型、测量
```

**在真实环境中测试的 alpha。** 自动化测试无法证明 Windows 上的系统声音被正确采集，也无法证明悬浮小窗在 Hyprland 下显示正常。每次合并前，我都会构建一个诊断版 alpha（检查器、详细日志、指标栏），PR 里列出**待确认检查**。每一项都写明平台和预期信号：一行日志、一个测量值、一个可见的行为。0.7.0 一共用了七个 alpha。一项检查绝不会悄无声息地消失：要么通过，要么注明理由和对应 issue 后推迟。

**CI 中的安全关卡。** 每个 PR 都要经过代码质量、测试、CodeQL、cargo-deny、Trivy、Gitleaks 和 Aikido。发布时还会生成 SBOM 和软件包的构建来源证明，Windows 安装包通过 Azure Artifact Signing 签名。对于面向公共机构的应用来说，能够验证自己安装的是什么，本身就是产品的一部分。

<Lesson title="智能体写代码，alpha 来裁决">
智能体写代码很快，单元测试也做得好。它们看不到的是真实的操作系统：一次在 Linux 上返回零个采样的视频导入，一次在 Windows 上第二次继续时中断录音的问题。这两个缺陷都是在 alpha 上发现的，而不是在 CI 里。
</Lesson>

<Lesson title="一项检查，一个信号">
在每项检查旁边写上预期信号（“两路流之间间隔约 1 秒，开头没有空白”），就能把一次模糊的手动测试变成可复现的测量，智能体也可以在日志中重新读取。
</Lesson>

<Lesson title="先整理，再添加">
每个次版本之前的清理，让代码库对智能体和对我都保持可读。没有它，每一批修复都只会增加代码，从不删除。
</Lesson>

## 还缺什么

0.7.0 是测试版，这个称呼名副其实：

- **没有 macOS**：应用没有在 macOS 上测试过；
- **没有自动更新**：每个新版本都需要手动下载；
- **悬浮小窗在 Hyprland 下还不完美**：它是一个普通的浮动窗口，略微偏大；修复计划在 0.7.1 中完成；
- **自动文件夹建议仍处于关闭状态**，直到我有数据来测量它的准确度；
- **硬件**：如果没有能运行这些模型的机器或共享服务器，Syntheo 就派不上用场。

1.0 会在真实会议中使用几周之后到来，而不是在完成某张功能清单之后。文档见 [docs.syntheo.studio](https://docs.syntheo.studio)，代码在 [GitHub](https://github.com/WillIsback/Syntheo)。
