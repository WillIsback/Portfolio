I ran a fleet of autonomous SRE agents on my real infrastructure: a home server, a DGX Spark and a VPS. The agentic loop worked. The value it produced for the infra, much less so. Here are the numbers, what held up, what broke, what trace analysis taught me, and what I'm keeping.

## The setup

The project was born for the NVIDIA Claw Agent Challenge in Paris: to show an SRE agent able to monitor, diagnose and repair an infrastructure with no human in the loop. I used [Hermes Agent](https://github.com/NousResearch/hermes-agent), an LLM served locally by vLLM on a DGX Spark (Qwen3.8), and a home-made MCP server with 59 tools covering my three machines: reads, Docker writes behind guardrails, sandboxed execution.

After the challenge, the fleet kept running on my home server with separate roles. A single agent, the conductor, is allowed to create tasks. The others return verdicts.

```text
cron */10 ─┐
           ├─▶ sre-conductor ──Kanban──▶ sre-monitor   (read-only scan, classifies, reports)
webhook ───┘   (sole dispatcher)          ├─▶ sre-diag      (root cause → verdict, applies nothing)
(crash, OOM)                              ├─▶ sre-doctor    (infra hot-fix from a verdict)
                                          ├─▶ sre-dev       (code fix in TDD → PR)
                                          └─▶ sre-reporter  (the only one to notify the human, Telegram)

alongside: sre-hygiene (incident cleanup), auto-eval (judges the traces), gardien (reminders)
observability: Langfuse (per-profile traces) + Julia-1, a small decision model that scores every step
```

## Reading the traces to evolve the agents

This is the part of the experiment that taught me the most. Every tool call by every agent ends up in Langfuse. Rather than reading transcripts by hand, I built a pipeline that detects failing calls, classifies them, and rewrites the verdict on the trace as a score.

The classification rests on a simple question: whose fault is it? Four categories came out of it.

Two things surprised me. First, seven deterministic rules are enough to classify 88% of the failures. The LLM only steps in on the residue, and its recurring classifications are meant to become new rules. This is the only place in the fleet where the system became less dependent on the model the longer it ran.

Second, the biggest category wasn't an agent error. Nearly half the failures fell under “capacity”: the agent wanted to do something reasonable and the environment forbade it. In autonomous mode, with no human to approve, code execution and the terminal are refused by the harness: 111 refusals for code execution, 69 for the terminal. These figures became a list of needs. I created narrow MCP tools to cover them: read-only command execution on an allowlist, sandboxed Python with no network or secrets, an HTTP probe limited to internal targets.

The “reasoning” failures told another story. A good share came from the intermediary tool used to call tools loaded on demand: the model got the arity wrong or called directly a tool that was supposed to go through it. These patterns were fixed in the agents' instruction files, not in the code: a skill dedicated to tool usage, examples of correct calls, and instructions removed when they contradicted each other.

The same work guided context-window management. Loading the schemas of 59 tools up front drowns the model. So tools are discovered on demand, from a list capped at 12,000 tokens, each profile has access only to the tools for its role (27 for diagnosis, for example), and loads automatically only its own skills. I also tuned the reasoning effort per role: low for orchestration, high for the probe that has to judge an ambiguous state.

The underlying difficulty is evolving an agent inside a protected environment. Every security restriction creates a new category of “capacity” failures. The agent needs tools, but the tools provided never cover all its real needs. So you have to measure what it tries to do, tell the legitimate need from the workaround, then add the narrowest possible tool. The 6 October audit showed it the other way round: when the tool was missing, the agent went through the terminal and the Docker socket. Some of the “capacity” failures that disappeared weren't solved. They were bypassed.

## What I'd do differently

<Lesson title="Trigger on an event">
An agent should work only when something new arrives: an alert, a PR, a document. Detection itself doesn't need an LLM. Today, Uptime Kuma and a 120-line script send the alerts straight to Telegram.
</Lesson>

<Lesson title="The LLM explores, the code consolidates">
Each pass by an agent should leave behind an artifact that reduces the need for the next pass: a rule, a test, a line of dataset. Tool-failure classification already did this by turning the LLM's classifications into rules. That's the mechanism that should have been generalized, not the scan.
</Lesson>

<Lesson title="Measure what the agent is trying to do">
Tool failures are the best specification of an agent's needs. Classifying them by responsibility (environment, reasoning, payload) says what to fix and where: a tool to add, an instruction to rewrite, or nothing.
</Lesson>

<Lesson title="Least privilege from day one">
An agent with a terminal has everything mounted in its container. The right boundary isn't a list of allowed tools, it's what the container can reach: a read-only Docker proxy and an SSH key limited to three commands validated on the host side.
</Lesson>

<Lesson title="Verify through the real path">
The gateway passes a filtered environment to the MCP servers. My tests went through docker exec, which sees everything: they were green, the agents were blind. Only a real agent session proves that a tool works.
</Lesson>

<Lesson title="Measure per profile from the start">
Per-profile trace attribution came late: two thirds of the tokens can't be tied to any agent. Without that measure, you don't see that one loop costs 60 times more than the useful work.
</Lesson>

## What I'm keeping

| Building block | What it brings |
| --- | --- |
| Rootless agent | Read-only Docker proxy and restart, SSH gateway with pinned commands, a single mounted key. |
| Tool-failure classification | Rules first, LLM on the residue, verdict rewritten on every Langfuse trace. |
| Julia-1 judge on Langfuse | Typed evaluation of every step and every turn, on CPU, wired in as a native evaluator. |
| OpenTelemetry collector | A single entry point: infra traces to Jaeger, LLM spans to MLflow. |
| Bitwarden secrets | Injected at launch, for Docker Compose as for the agents, nothing on disk. |

The fleet remains reproducible from a git tag. Its crons are paused, not deleted. The next experiment starts from a narrower hypothesis: giving every LLM-consuming service its own account and its own keys through the MLflow gateway.
